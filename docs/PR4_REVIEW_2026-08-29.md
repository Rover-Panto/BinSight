## Findings

### P1: Invalid model metadata and incompatible runtimes still reach the loader

`ml/src/serve.py:70-104` accepts adjacent major versions, ignores minor/patch differences and allows a dependency whose version cannot be established. Its special-case rejection of the word `impossible` does not validate versions. Independent guard tests reached the mocked `joblib.load` with NumPy 1.26.4 against a 2.5.1 manifest, XGBoost 3.4.0 against 3.4.1, an absent dependency, and a malformed version string.

`serve.py:158-184` checks five required keys and agreement between two feature lists, but not the runtime schema, target semantics or availability ordering. Unknown schema 99, a missing target definition, a declaration of 100% support, an invented feature in both files, missing availability metadata, and availability before selection all reached the loader. `ReviewModel` and `TwelveHourModel` also appear in the production estimator allow-list at lines 51-57.

Fix: validate a typed manifest before deserialization. Require the reviewed schema, the actual runtime feature list, the 90% service target, complete dependency declarations and ordered UTC provenance. Use parsed exact versions for this joblib bundle, or an explicit compatibility policy backed by tests; missing versions must fail closed. Keep test doubles in tests rather than the production allow-list. A checksum and declared class name do not make an untrusted pickle safe.

The version restriction follows the persistence requirements described by [scikit-learn](https://scikit-learn.org/stable/model_persistence.html#workflow-overview) and XGBoost's distinction between [portable model files and memory snapshots](https://xgboost.readthedocs.io/en/stable/tutorials/saving_model.html). This finding concerns reproducibility and validation, not a claim that this checked-in artifact is malicious.

### P1: A faulty latest reading still produces an available forecast

`serve.py:315-319` degrades quality only when every confidence flag is zero. With a valid 20% reading followed by a flagged 95% reading, the shipped model returns `status: available`, `confidence_flag: 0`, and **0.66 hours** to the service threshold. PR1 could prioritize collection using that invalid reading.

Fix: validate and select usable readings before feature construction. Exclude flagged readings from fill/rate features and return an explicit degraded state when the latest observation fails quality checks. If a last-good estimate is retained, identify it, measure freshness from its own timestamp, and do not present it as a current healthy forecast.

Two related cases remain: duplicate copies of one observation return `available` rather than `cold_start`, because the code counts rows before deduplication; a NaN fill yields a `model_error` record that still contains NaN, so strict JSON serialization fails. Count distinct usable observations and return JSON-safe nulls for unknown values. These checks must hold per configured bin without converting unknown fill into zero.

### P2: Equivalent observation timestamps change the prediction

`serve.py:449-453` normalizes temporary Series for filtering but never assigns those UTC values back to history. `ml/src/features.py:43-45` therefore extracts calendar features from the original timezone. The same two readings at 09:00/10:00 UTC and 17:00/18:00 +08:00 produce **5.05 hours** and **13.04 hours**, respectively. Mixing offsets in one history returns `model_error`.

Fix: carry normalized timestamps through sorting, deduplication, rate calculation and feature construction. Use one documented model timezone for calendar features in training and serving. Extend the existing timezone test to transform observations and receipts, not only `decision_at`; compare numeric forecasts and horizon fields as well as status.

### P2: Retraining and default serving use different model copies

The new default resolver in `serve.py:131-139` prefers `ml/binsight_ml/models`, but `ml/src/train.py:40,172-173` still writes only `ml/models`. `ml/run_all.sh:21-24` trains and then invokes the default server, so its smoke test can use the old packaged model. A wheel also packages only the copied bundle, not the newly trained output.

Fix: define one authoritative build output and a deliberate promotion step into the package, or pass the freshly trained bundle explicitly during the pipeline and verify its hash against the wheel before release. Add a regression that changes the training output's version/hash and checks what the smoke test and installed provider load. Do not delete historical model evidence to resolve the duplicate paths. This finding follows the source paths; this review did not rerun full model training.
